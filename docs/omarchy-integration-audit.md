# Omarchy and personal configuration audit

**Assessment date:** 2026-10-12  
**Installed Omarchy:** `4.0.4-1` (`/usr/share/omarchy`; package reports the same version)  
**Installed components relevant here:** Hyprland `0.56.2-2`, Quickshell `0.3.1-1`, Neovim `0.12.5-1`, Ghostty `1.3.1-2`, Foot `1.28.0-1`.

This is a read-only assessment of the active user files, this dotfiles worktree, and the installed package. The installed release and its `/usr/share/omarchy` code are the baseline; online material was checked against the official `v4.0.4` tag. Later upstream branch behavior is not assumed to be installed.

## Summary

This is a substantial, deliberate customization of Omarchy rather than a wholesale replacement. Hyprland explicitly bootstraps and imports Omarchy defaults before personal overrides. The personal shell config replaces the stock bar layout but retains the core Omarchy menu, indicators, keyboard layout, agent, Bluetooth, network, audio, monitor, and power widgets; it adds personal widgets and panel plugins. Personal keybindings route capture, lock, app menus, and notification actions back through Omarchy commands.

The most concrete integration gap is Neovim theme propagation. Omarchy stages a `neovim.lua` for the current theme, but the active personal Neovim config imports only its own Lazy.nvim plugin directory, which does not import that staged file. A PontuArch palette bridge is confirmed in the live config and in its authoring repository: the backend generates the palette and attempts to reload running Neovim servers. The live generated palette says Tokyo Night while Omarchy's current theme and staged Neovim theme say Catppuccin. The code exists, but this inspection could not verify whether the PontuArch daemon is enabled or running. The two generated theme inputs currently disagree.

## Integration map

### Hyprland, application launch, and hardware configuration

The active `~/.config/hypr/hyprland.lua` runs Omarchy's bootstrap, requires `default.hypr.omarchy`, then loads personal monitor, input, binding, appearance, autostart, and routing modules. This retains package defaults and adds personal policy. The active user `autostart.lua` is unchanged from the packaged config. Personal monitor and input files contain machine-specific choices; their existence is expected user customization, not evidence of lost Omarchy support.

The personal bindings deliberately replace a large set of package app shortcuts and some utility chords, then expose grouped app/settings menus through `omarchy-menu`. The source still calls Omarchy for lock, screenshots, screen recording, clipboard history, notification dismissal, audio, and shell plugins. Capture is therefore routed through Omarchy's command suite even though the shortcut map differs. The custom menu extension adds app categories and setup routes. The main tradeoff is discoverability/parity: stock chords such as the default editor, app, and notification shortcuts have been reassigned or unbound; the custom menu and help routes compensate for many of them.

No live Hyprland keymap result was available from the sandbox: `hyprctl binds -j` did not return IPC data. Static config-chain evidence is used instead; the failed IPC call is not evidence that Hyprland or its bindings are absent.

### Shell, plugins, notifications, capture, lock, and idle

The active `~/.config/omarchy/shell.json` is a full user layout. It changes stock widget placement and selection, adds `omarchy.media`, personal tray/workspaces/system-monitor widgets, and enables `pontual.tasks`, `pontual.search`, and `foamy.notification-center`. The package's default weather and system-update widgets are not present in the user layout; add them back if their bar visibility is desired. The layout retains Omarchy's core menu, indicators, keyboard layout, agents, Bluetooth, network, audio, monitor, and power widgets. Idle timings remain the package values: screensaver at 150 seconds and lock at 300 seconds.

The configuration routes notification history/dismissal to Omarchy shell IPC and uses a third-party notification center widget. It retains native Omarchy capture and lock commands. This is a mixed shell that uses the built-in plugin system, not a replacement bar/notification stack. Live plugin directories exist under `~/.config/omarchy/plugins`; Omarchy's installed plugin discovery and source code are present. Whether the shell process and all IPC endpoints were responding could not be checked in this sandbox and is not inferred from that limitation.

The custom `~/.config/omarchy/themed/shell.toml.tpl` is an active theme template, and the staged `current/theme/shell.toml` is an expected generated theme output. The only checked-in theme hook in `theme-set.d` is a `.sample`; Omarchy ignores sample hooks. No active theme-set hook is visible in the inspected live hook directory.

### Neovim ownership and theme propagation

The live `/home/pontual/.config/nvim` is a plain directory, not a symlink or Git checkout. Its README records the original upstream clone URL `github.com/BrenoCRSilva/neovimrc`; the current authoring/deployment source is `/home/pontual/tasks/omarchy-ricing/PontuArch/env/.config/nvim`, in the `PontuArch` repo (`origin` is `github.com/BrenoCRSilva/PontuArch`, branch `omarchy-ricing`). PontuArch's `env/dotfiles.manifest` includes `.config/nvim`; `scripts/apply.sh` copies that authored tree to `$HOME/.config`, and `scripts/capture.sh` mirrors the live tree back into `env/`. Thus the likely durable owner is `PontuArch/env/.config/nvim`; do not add a competing copy to this dotfiles worktree. The live directory is deployed content, not the authoring source.

The two trees currently have drift to reconcile before a future apply: `lua/brenocrs/plugin-keymaps.lua`, `lua/brenocrs/set.lua`, and `lua/plugins/minuet-ai.lua` differ; `lua/plugins/vectorcode.lua` exists only in `env/`; `lazy-lock.json`, `lua/plugins/copilot.lua`, and generated `lua/pontuarch-palette.lua` exist only live. The original upstream README is useful provenance, not the current deployment owner.

The live `init.lua` is a one-line entry point to `require("brenocrs")`. That module sets the space leader, loads options and remaps, then `plugin-keymaps`, `brenocrs.lazy`, and `pane-style`; Lazy.nvim imports `plugins` only. This is a custom Lazy.nvim setup, not LazyVim. Its catalog in `env/.config/nvim/lua/plugins/colorschemes.lua` declares lazy-loaded Tokyo Night, Gruvbox, Sonokai, Dracula, VSCode, OneDark, Nord, GitHub, Kanagawa, and Catppuccin plugins. Rose Pine remains the palette fallback. These existing pieces can be retained while changing only the adapter seam.

The confirmed PontuArch producer is `PontuArch/backend/domains/theme/generator.rs`: `generate()` writes `~/.config/nvim/lua/pontuarch-palette.lua` and calls `reload_nvim()`. It is invoked at daemon startup in `backend/src/main.rs`, on curated theme apply and autocolor in `backend/domains/theme/service.rs`, and by the config watcher. `reload_nvim()` searches Neovim sockets below `$XDG_RUNTIME_DIR` (fallback `/run/user/1000`) and sends Lua to reload `pontuarch`. The user's Lua adapter is `env/.config/nvim/lua/pontuarch.lua`; it chooses a declared native colorscheme and lazy-loads its plugin, otherwise drives Rose Pine from the generated palette. `plugins/rose-pine.lua` calls `pontuarch.apply()` at startup and adds `:PontuarchReload`; lualine rereads the same generated palette and rebuilds after `ColorScheme`. These are concrete implementation paths, not evidence the daemon is installed/enabled/running. PontuArch user service unit files are present in its source tree, but runtime service state was not verified; blocked/no-result service or socket queries are not treated as absence.

Omarchy's current theme is Catppuccin and its staged `/home/pontual/.local/state/omarchy/current/theme/neovim.lua` is a Catppuccin Lazy spec. The generated PontuArch palette currently declares Tokyo Night. The stock staged file is not imported by `brenocrs.lazy.lua`, and its `LazyVim/LazyVim` option is not consumed by this personal config. The installed `/usr/share/omarchy/default/themed/neovim.lua.tpl` emits an Aether/LazyVim spec, so using it verbatim would not adapt this config. Omarchy's installed theme-set path supports user `.tpl` files under `~/.config/omarchy/themed/`, renders them into `~/.local/state/omarchy/current/theme/`, and invokes executable user `theme-set.d` hooks after activation. The active live hook directory currently contains only a sample; the dotfiles worktree tracks the same sample. Its absence is evidence that no authored user hook is present at these paths, not that no external process can trigger the PontuArch code.

The integration gap is therefore competing theme authority: Omarchy stages a theme input, while PontuArch owns a second palette generator and reload attempt, and the personal adapter consumes only the latter. Prefer Omarchy as the sole theme-state authority on Omarchy hosts. During the current transition, the personal plugin catalog, mappings, and Lua adapter are authored in PontuArch `env/.config/nvim`; the dotfiles worktree owns the Omarchy template and hook. If the user chooses the reconciled consolidation, both authored config and the capture/apply/sync tooling move under `dotfiles/env`, so there is one durable authoring owner. The adapter should read an Omarchy-generated, personal-schema palette in current theme state, with a graceful fallback if Omarchy state is absent. The template should emit the adapter's small stable schema (selected supported native colorscheme plus palette tokens if required) from Omarchy color placeholders, not LazyVim instructions. A single user `theme-set.d` hook should reload each existing Neovim socket after the theme output is staged; new sessions should read the same staged file at startup. In PontuArch, gate its legacy Neovim palette writer/reloader off on Omarchy hosts so it cannot overwrite Omarchy's active input; no PontuArch daemon dependency is needed. PontuArch can retain generation for its other supported apps as its workflow agent proposes. Keep runtime-generated palette state out of the env mirror; explicitly ignore it during capture and do not deploy it during apply. `env/.config/nvim/lua/pontuarch.lua` is authored code; `env/.config/nvim/lua/pontuarch-palette.lua` should not become a tracked authored file.

This describes the current transition ownership: PontuArch owns the authored Neovim env tree and adapter; dotfiles owns the Omarchy template and hook. The reconciled longer-term proposal is to consolidate the authored tree and Bash capture/apply/sync tooling into `dotfiles/env` if the user chooses that migration, keeping the Neovim adapter/catalog and Omarchy template/hook under that single authoring owner. Until then, do not create a second authored Neovim copy in dotfiles. On Omarchy, the staged Omarchy palette remains the single theme-state source and the one theme-set hook reloads existing sessions; the Neovim adapter reads that same state at startup. Gate PontuArch's competing Neovim palette/reload outputs on Omarchy, without depending on a PontuArch daemon. The consolidation is a proposal, not an implementation decision. User preferences still needed before implementation include whether non-Omarchy hosts should retain PontuArch-generated palettes or use the static Rose Pine fallback, and which personal UI/plugin/keymap areas to revisit. No move to LazyVim is needed or proposed.

## Focused Neovim redesign proposal

1. **Make Omarchy the only active theme-state producer on Omarchy.** Add a personal template such as `dotfiles/.config/omarchy/themed/nvim-palette.lua.tpl` that writes a small documented palette schema into `~/.local/state/omarchy/current/theme/nvim-palette.lua`. Map Omarchy's colors to the fields the personal adapter needs and choose an installed native colorscheme by an explicit mapping/policy. Do not import the staged `neovim.lua` LazyVim spec wholesale. A later supported-template change could emit a compatible Lazy plugin spec, but this is not needed to preserve the current catalog.
2. **Keep the current adapter owner during transition; consolidate if chosen.** Until ownership moves, modify the adapter and consumers only in `PontuArch/env/.config/nvim/`; do not duplicate them into this dotfiles repo. If the user chooses the reconciled consolidation proposal, move the authored tree and Bash tooling into `dotfiles/env` as one migration. In either arrangement, retain the existing plugin catalog, prefer Omarchy's palette on Omarchy, fall back safely elsewhere, and gate `PontuArch/backend/domains/theme/generator.rs` from writing/reloading Neovim on Omarchy (no daemon dependency). Preserve the current `env/.config/nvim/lua/plugins/colorschemes.lua` set unless the user chooses to prune themes.
3. **Refresh existing and new sessions from the same generated state.** During the current split, the template and a single executable hook belong under `dotfiles/.config/omarchy/`; after a chosen consolidation, keep them in the consolidated `dotfiles/env` authoring mirror. The hook uses the stable `nvim --server … --remote-send` reload interface after Omarchy stages the output, handles zero/multiple sockets, and does not start Neovim just to set its theme. Startup in the adapter reads the same staged palette, so later-launched instances match. Omarchy hook behavior is documented in the installed v4.0.4 source and [official theming guide](https://github.com/omacom/omarchy/blob/v4.0.4/docs/theming.md).
4. **Preserve capture/apply without versioning generated state.** During the transition, keep `.config/nvim` in PontuArch's manifest as authored config. If consolidation is chosen, include the authored tree and Omarchy template/hook in `dotfiles/env` under one manifest/owner. In either layout, do not capture or apply staged `current/theme/nvim-palette.lua` or live `lua/pontuarch-palette.lua`; add the appropriate ignore/scrub rule so capture excludes generated output and apply never overwrites it. The exact rule belongs in PontuArch's workflow plan/implementation during the current split, or in the consolidated tooling if chosen. Reconcile existing live-vs-env drift (three differing files, live-only lockfile/copilot/generated palette, env-only vectorcode) before any apply.
5. **Validate only during a later implementation.** Exercise template rendering for representative light/dark themes; validate schema and colors; verify a fresh Neovim chooses the generated theme and an already-running server reloads it; check that no daemon writes a competing palette on Omarchy; check the non-Omarchy fallback. No builds, tests, theme switches, or live edits were performed for this proposal.

Optional personal-config cleanup is separate from theme integration: (a) `plugin-keymaps.lua` installs global `<leader>df` for closing all folds when `nvim-ufo` lazy-loads, while `plugins/dadbod.lua` also declares global `<leader>df` for `DBUIFindBuffer`; choose one mapping or make one buffer/plugin-specific after checking intended use. (b) `plugins/noice.lua` hardcodes `nvim-notify` background to `#000000`, which can diverge from the selected Omarchy palette; prefer deriving it from active highlights/palette or preserving that black backdrop if intentional. (c) Lualine currently cache-busts and reads `pontuarch-palette` for its base color, while also rebuilding from current colorscheme highlights on `ColorScheme`; simplify it to one authoritative palette/highlight path alongside the adapter. Keep the existing plugins and keymaps by default; treat cleanup as user-selected, not a migration prerequisite.

For shell plugin work, Omarchy's v4.0.4 shell documents built-in plugin cloning and user plugin installation. The installed shell code and the live plugin directories corroborate those capabilities. [Omarchy v4.0.4 shell README](https://github.com/omacom/omarchy/blob/v4.0.4/shell/README.md)

## Scope and limits

Read-only inspection covered installed package versions and paths; package defaults and commands; the deployment plan and tracked/live file comparisons; active Hyprland, shell, terminal, and Neovim config chains; the assigned PontuArch worktree's Neovim env mirror and generator source; Omarchy's installed theme-set/template/hook/plugin code; active theme identifiers and generated theme outputs; and relevant official v4.0.4 sources. No live config was changed, no theme was switched, and no package/service operation was run.

The sandbox blocked compositor IPC. An initial headless Neovim path probe used `-u NONE` but omitted `-i NONE`, so Neovim attempted to create a ShaDa temporary file and the read-only filesystem denied it; no user plugins were loaded. I then repeated only the path probe with `-u NONE -i NONE`, which returned the config and data paths without loading plugins or writing state. Active graphical services, live keybindings, shell IPC health, Neovim sockets, and whether the PontuArch daemon is enabled or running were not verified. The audit does not treat those blocked checks as missing components. A first-pass search of this dotfiles worktree and selected home config/bin/systemd directories did not find the palette generator; inspection of the assigned PontuArch worktree subsequently confirmed it at the paths above. No broader PontuArch architecture audit was performed.
